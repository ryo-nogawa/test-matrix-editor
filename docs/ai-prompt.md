# AIへの指示文（案）

要件定義書 5.7 の指示文の案です。ツールの「指示文コピー」ボタンで、この指示文とMarkdownの表を一緒にコピーする想定です。
書式は [Markdown書式仕様書](markdown-format.md) に合わせています。

- 版：0.3（2026-10-27）

| 版 | 日付 | 変更内容 |
| --- | --- | --- |
| 0.1 | 2026-10-27 | 初版 |
| 0.2 | 2026-10-27 | 単一障害のルール（異常系の条件は1つの試験に1つだけ）を追加 |
| 0.3 | 2026-10-27 | 期待値（出力の行）は参考資料がある場合のみ記入するよう制限。機能の行は表の上から順に処理されるとみなすルールを追加。例を参考資料なしの書き方に変更 |

## 1. 使い方

ツールの「指示文コピー」ボタンを押すと、下の指示文の `{{MATRIX}}` を画面の条件の表（試験項番の列なし）に置き換えて、まとめてコピーします。
指示文はビルドのたびにこのファイルから取り出してツールに埋め込むため、**指示文を直すときはこのファイルを直してビルド**してください（`` ````text `` で囲まれた部分が対象です）。

試行するときは、次の手順で行います。

1. ツールの「指示文コピー」でコピーする
2. 社内のAIに貼り付けて送る
3. 返ってきた表を「3. 試行時の確認ポイント」で確認する

## 2. 指示文

````text
あなたはソフトウェアテストの設計者です。
以下の「条件の表」をもとに試験ケースを設計し、試験項番の列を追加して、各セルに印を付けた表を返してください。

# 表の読み方
- 表の左側の列は、左から順に親・子・孫の階層になっている条件の定義です。
- 試験項番の列の直前にある列は「具体値」で、その条件の具体的な値です。
- 種類の列は、入力（事前条件）・機能（処理）・出力（結果）の分類です。

# 試験ケースの考え方
- 1つの試験項番（列）が、1つの試験ケースを表します。
- 各試験ケースで、どの条件が成り立つかを印で表します。
- 同じ親を持つ条件（例：同じ「項目」の下にある複数の「パターン」）は、1つの試験ケースの中では通常1つだけ選びます。
- エラーになる条件（異常系）は、1つの試験ケースに1つだけ含めてください。正常系の条件と組み合わせ、どの条件でエラーになったかを区別できるようにします。
- 機能の行は、表の上から下の順に処理されるものとみなします。
- ある条件で処理が止まる場合（エラーで終了するなど）、それより後の処理の条件には「−」を付けます。
- 入力・機能の行には、すべて少なくとも1つの試験ケースで「○」が付くようにしてください（出力の行は、次の「期待値の扱い」に従います）。
- 不要な重複がないよう、できるだけ少ない試験ケースで網羅してください。

# 期待値（種類が「出力（結果）」の行）の扱い
- 期待値は、設計書・仕様書などの参考資料に書かれている内容に基づいてのみ記入してください。推測や一般的な慣例で記入してはいけません。
- このメッセージに参考資料が添付または貼り付けられていない場合は、出力の行をすべて空欄にしてください。
- 参考資料がある場合でも、資料から判断できない期待値は空欄にしてください。

# 印の種類（この3種類以外は使わない）
| 印 | 意味 |
| --- | --- |
| ○ | 確認する観点（この試験でこの条件が成り立つ・この結果を確認する） |
| − | 手前の条件で処理が止まり、この条件には到達しない |
| 空欄 | 該当しない（何も書かない） |

# 出力の書式（厳守）
1. Markdownの表を1つだけ返してください。表はコードブロック（```markdown）で囲んでください。
2. 左側の列（見出し・値・行の順番・行の数）は一切変更しないでください。行の追加・削除・並べ替え・言い換え・省略をしないでください。
3. 具体値の列の右に、試験項番の列を追加してください。
4. 試験項番の見出しは、半角数字3桁の連番（001, 002, 003, …）にしてください。「試験項番」などの見出しは付けないでください。
5. 見出しは1行だけにしてください。セルの結合はしないでください。
6. すべての行で、列の数を見出し行と同じにしてください。空欄のセルも「|  |」として省略せずに書いてください。
7. 印は「○」「−」「空欄」のみを使ってください。「×」「✓」「●」などは使わないでください。

# 補足説明
表のコードブロックの後に、各試験項番の狙いを「001: ～」の形の箇条書きで1行ずつ書いてください（表にはしないでください）。
空欄にした期待値がある場合は、続けて「期待値の未記入」として、空欄にした理由と、記入するために必要な資料・情報を箇条書きで書いてください。

# 例
条件の表：
| 種類 | 対象 | 項目 | パターン | 具体値 |
| --- | --- | --- | --- | --- |
| 入力 | ログインAPI | リクエスト | 必須項目あり | login() |
| 機能 | 会員確認 | 会員情報の検索 | 見つかる | true |
| 機能 | 会員確認 | 会員情報の検索 | 見つからない | false |
| 機能 | 状態確認 | アカウント状態 | ロック中 | locked |
| 出力 | レスポンス | 結果コード | エラー | ERR |

返す表：
| 種類 | 対象 | 項目 | パターン | 具体値 | 001 | 002 |
| --- | --- | --- | --- | --- | --- | --- |
| 入力 | ログインAPI | リクエスト | 必須項目あり | login() | ○ | ○ |
| 機能 | 会員確認 | 会員情報の検索 | 見つかる | true |  | ○ |
| 機能 | 会員確認 | 会員情報の検索 | 見つからない | false | ○ |  |
| 機能 | 状態確認 | アカウント状態 | ロック中 | locked | − | ○ |
| 出力 | レスポンス | 結果コード | エラー | ERR |  |  |

- 001: 会員情報が見つからない場合（アカウント状態の確認には到達しない）
- 002: 会員情報は見つかるが、アカウントがロック中の場合

期待値の未記入：
- 参考資料が渡されていないため、出力の行はすべて空欄にした
- 記入には、会員情報が見つからない場合とアカウントがロック中の場合の応答仕様（結果コード）が分かる設計書が必要

※ 上の例は書式の説明用で、参考資料がない場合の書き方です。実際の試験ケースは、下の条件の表（と、渡された参考資料）だけをもとに設計してください。

# 条件の表
{{MATRIX}}
````

## 3. 試行時の確認ポイント

返ってきた表を、次の観点で確認してください。崩れ方の傾向が分かれば、指示文と読み込み処理（[書式仕様書](markdown-format.md) 6章）の両方を調整できます。

### 書式（ツールで読み込めるか）

- [ ] 表が1つだけか。コードブロックで囲まれているか
- [ ] 左側の列が出力時から変わっていないか（行の追加・削除・言い換え・並べ替え）
- [ ] 試験項番が `001` からの3桁連番になっているか
- [ ] すべての行で列の数がそろっているか（末尾の空欄を省略していないか）
- [ ] 印が ○ / − / 空欄 だけか。別の文字（◯、O、ー、× など）が混ざっていないか
- [ ] 「試験項番」の見出し行が余分に入っていないか

### 内容（試験として妥当か）

- [ ] 同じ項目の中で、1つの試験に複数のパターンを選んでいないか
- [ ] 1つの試験に、異常系の条件が2つ以上含まれていないか
- [ ] 参考資料を渡していないのに、出力の行に印を付けていないか
- [ ] 参考資料を渡した場合、出力の行の印が資料の記述と一致しているか
- [ ] 「−」が、処理が止まった後の条件にだけ付いているか
- [ ] ○ が1つもない条件の行がないか
- [ ] 試験の数が多すぎ・少なすぎないか

### 規模

- [ ] 行・列が多い表（例：行50 × 列100以上）でも、列の位置がずれずに印が付くか
  - ずれる場合は、表の縦横の入れ替えや分割を検討する（要件定義書 7章）
